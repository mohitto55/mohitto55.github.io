# Chapter 01: 도메인 모델 시작하기

# 한줄 요약
도메인은 소프트웨어로 해결하고자 하는 문제 영역을 말하며 도메인 모델은 이를 개념적으로 표현한 것을 말한다.


# 도메인이란 무엇인가?
도메인은 소프트웨어로 해결하고자 하는 문제 영역을 뜻한다.
도메인에는 하위 도메인이 존재하며 카카오톡 채팅 시스템으로 치자면 채팅 하위 도메인으로 이모티콘 시스템, 선물 보내기 등이 있다.
도메인은 여러 하위 도메인이 연동하여 완성된 기능을 제공한다.

## 내부 시스템만 도메인일 필요는 없다.
이모티콘을 구매하기 위해서는 결제가 필요하다. 결제 기능을 외부 PG사가 제공하더라도, 우리 서비스가 다뤄야 할 결제 성공·실패·취소 규칙은 여전히 도메인에 속한다. 다만 PG사의 내부 구현은 외부 시스템의 관심사이며, 우리 모델에 모두 담을 필요는 없다.

# 도메인 모델이란
도메인을 개념적으로 표현한 것을 말한다.
도메인을 이해하기 위한 개념 모델이다. 현실을 완전히 복사하는 것이 아니라, 현재 해결하려는 문제에 필요한 개념과 관계·규칙만 선택해 표현한다.

## 도메인 모델 작성시 각 도메인 마다 
도메인 모델마다 같은 용어가 등장할 수 있다.
이름은 같지만 하위 도메인마다 의미가 다를 수 있다.
따라서 이름만 같다는 이유로 같은 모델로 취급해서는 안 된다.

그러므로 여러 하위 도메인을 하나의 다이어그램에 모델링하면 안 된다.
이모티콘 시스템과 선물 보내기를 하나의 다이어그램에 함께 표시하면, 각 모델의 의미를 제대로 이해하는 데 방해가 된다.
하위 도메인마다 별도의 모델을 만든다.

## 도메인 모델의 기본 패턴

| 영역 | 설명 |
| --- | --- |
| 사용자 인터페이스 | 사용자의 요청을 받고 결과를 보여준다. |
| 응용 계층 | 사용자가 요청한 기능을 실행하도록 흐름을 조정한다. |
| 도메인 | 시스템이 제공해야 할 핵심 도메인 규칙을 구현한다. |
| 인프라스트럭처 | 데이터베이스·메시징 시스템 등 외부 시스템과의 연동을 처리한다. |

이 중 도메인 계층이 도메인의 규칙을 구현한다. 핵심 규칙을 도메인 모델에 모아 두면 규칙 변경이 다른 계층에 덜 전파되고, 코드만 보아도 업무 규칙을 파악하기 쉬워진다.

# 도메인 모델 도출하기
도메인 모델을 만드려고 하면 막막할 수 있다.
뛰어난 개발자는 도메인 모델의 이해 없이 코딩을 시작할 수 없다.
도메인 모델을 만들기 위해서는 도메인을 이해해야 하며, 기획서·고객 요구사항·도메인 전문가와의 대화 등을 통해 지식을 얻는다.
이를 바탕으로 도메인 모델 초안을 만들고, 구현과 피드백을 거치며 계속 수정한다.

도메인 모델링의 기본 작업은 모델을 구성하는 핵심 구성요소, 규칙, 기능을 찾아내는 것이다.

## 규칙 예시
온라인 주문을 예로 들면 다음과 같은 규칙을 도출할 수 있다.

- 주문은 최소 한 개 이상의 주문 항목을 가져야 한다.
- 결제 완료 전에는 배송을 시작할 수 없다.
- 배송 준비가 시작된 주문은 일반 취소할 수 없다.

이 규칙은 화면이나 DB 제약 조건에 흩어 두기보다 Order 같은 도메인 모델의 행동으로 표현해야 한다. 그래야 API나 배치 등 진입점이 달라져도 같은 규칙이 유지된다.

# 엔티티와 밸류
도메인 모델을 작성하면 내부를 크게 엔티티와 밸류로 구분할 수 있다.

## 엔티티
- 각 객체마다 식별자를 지닌다.
- 속성이 같아도 식별자가 다르면 서로 다른 객체다.
- 식별자는 엔티티가 생성되고 삭제될 때까지 유지된다.

예를 들어 주문 번호가 다른 두 주문은 주문 항목과 금액이 우연히 같아도 서로 다른 Order 엔티티다.

## 밸류 타입
- 개별 식별자보다 **값 자체**로 의미를 갖는 타입이다.
- 값이 같으면 같은 것으로 비교한다.
- 관련된 데이터와 규칙을 한 단위로 묶어 의미를 드러낸다.
- 가능한 불변 객체로 구현하는 것이 안전하다.

예를 들어 Money는 금액과 통화를 함께 표현하는 밸류다. 단순 `int`로 가격을 다루면 통화·음수 금지 같은 규칙이 흩어지지만, Money 타입은 생성 시 검증하고 금액 계산 기능을 제공할 수 있다.

## 내가 이해한 흐름

사용자와 도메인 전문가가 사용하는 업무 언어에서 개념과 규칙을 찾는다. 그중 문제 해결에 필요한 것만 추상화해 도메인 모델을 만들고, 엔티티·밸류 같은 객체로 코드에 표현한다. 이후 요구사항이 바뀌면 도메인 모델과 코드도 함께 바꾼다. 즉 DDD의 시작은 기술 선택이 아니라 **문제 영역을 이해하고 언어와 규칙을 코드에 반영하는 일**이다.
