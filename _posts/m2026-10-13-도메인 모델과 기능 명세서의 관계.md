> 도메인 문서화에서 중요한 것은 하위 항목을 많이 만드는 것만이 아니라, 업무의 분류·모델의 관계·사용자 기능·구현 흐름을 구분하고 서로 연결하는 것이다.

이번 고민의 출발점은 Orbit에서 채팅 도메인과 하위 도메인, 기능 명세, 테스트를 제대로 정리하려는 것이었다. 모델 설정·채팅방 설정·First Play까지 문서화하는 과정에서, 무엇을 도메인으로 묶고 어느 수준까지 설명해야 하는지가 핵심 문제로 드러났다.

처음에는 채팅의 여러 책임이 하나에 몰려 있었다. 채팅방만 해도 모델 설정, 진입 조건, 대화 진행, 이력, 기억 등 구분할 책임이 많은데, 이를 충분히 나누지 않으면 각 영역이 무엇을 맡는지 보이지 않았다. Obsidian의 기존 채팅 도메인 자료를 확인하라고 한 이유도 기존에 정리한 개념과 하위 영역을 놓치지 않기 위해서였다.

반대로 하위 항목을 늘린 뒤에는 구조가 너무 복잡해 보였다. 어떤 항목은 업무 영역이고, 어떤 항목은 개별 기능이며, 어떤 항목은 모델이나 구현 요소처럼 보여서 같은 계층에 놓아도 되는지 의문이 생겼다. 개별 객체 수준까지 내려간 것은 아닌 것 같은데도 복잡하다면, 단순히 항목 수보다 서로 다른 추상화 수준이 섞인 것이 문제일 수 있다.

도메인 계층을 설명하려던 문서가 세부 기능 설계서처럼 작성되는 점도 걸렸다. 도메인 문서에서는 그 영역이 왜 존재하고, 어떤 개념과 상태를 소유하며, 어떤 규칙을 지키는지 드러나야 한다. 요청 처리 순서, 서비스 호출, 저장 방식까지 중심에 들어오면 도메인을 설명하는 글인지 구현을 설명하는 글인지 흐려진다.

그런데 기능 명세 쪽에서는 정작 어떤 기능이 있는지 알아보기 어려웠다. 서버가 무엇을 검사하고 저장하는지는 적혀 있어도, 대화를 시작하고, 답장을 다시 생성하고, 특정 턴에 아이템을 얻는 기능이 있는지 바로 찾기 어려웠다. 기능을 이해하기 쉬운 이름으로 보여줄 필요는 있지만, 사용자 기능 전체를 도메인 아래의 규칙 명세에 넣는 것이 맞는지는 별도의 문제였다.

트리거와 N턴 후 아이템 획득은 이 혼란을 구체적으로 드러낸 사례였다. 트리거가 문서에서 빠지거나, N턴 후 아이템 획득이 트리거 아래에만 들어가 있으면 기능의 목적과 실행 수단이 섞인다. 이번 대화에서는 N턴 후 아이템 획득을 대화 진행의 기능으로 보고, 트리거를 대화 진행 아래에서 조건과 액션을 담당하는 영역으로 정리했다. 실제 아이템의 소유권과 지급 책임까지 모두 대화 진행이 소유한다고 볼 수는 없다. 같은 사용자 기능 안에서도 여러 도메인이 각자의 책임을 맡는다.

이후에는 문서의 상하위 관계와 실제 코드의 관계가 맞는지 의문이 생겼다. 문서에서는 채팅 → 채팅방 → 대화 진행 → 트리거로 묶었지만, 실제 구현은 여러 패키지와 서비스에 흩어져 있다. 구현을 나누는 것 자체는 괜찮다. 다만 흩어진 구현을 무엇이 하나의 상위 도메인으로 묶는지, 그 소속과 책임이 코드와 문서에서 충분히 드러나지 않는 느낌이 있었다.

이때 같은 응용 서비스가 호출한다는 이유만으로 하나의 도메인이라고 판단해서는 안 된다는 구분이 필요해졌다. 실제 코드에서 ChatTurnService는 실행을 조율하고 BaseRoom은 대화 상태와 행위를 맡는다. 응용 서비스의 호출 관계는 구현을 이해하는 자료지만, 도메인을 나누는 근거는 공통 업무 개념, 모델이 소유한 상태와 행위, 함께 지켜야 하는 규칙에서 찾아야 한다.

책의 100페이지 그림 3.3처럼 모델과 코드가 명확하게 대응하면 좋겠다는 생각도 여기서 나왔다. 대화에서 확인한 Bus·Net·LayoutRule 예제는 개념 사이의 관계와 행위가 코드에 드러나는 모델이었다. 실제 시스템의 모델들이 서로 엮이는 것은 자연스러우며, 그 관계를 표현하려면 단순한 상하위 트리만으로는 부족할 수 있다.

따라서 다음 세 가지를 구분할 필요가 있다.

| 관점 | 알고 싶은 것 | 예시 |
|---|---|---|
| 업무의 도메인 분류 | 어느 업무가 어느 범위에 속하는가 | 채팅 → 채팅방 → 대화 진행 → 트리거 |
| 도메인 모델 관계 | 어떤 모델이 상태와 행위를 가지며 서로 어떻게 관계하는가 | 방의 진행 상태, 모델 선호, 트리거 조건과 결과, 지급 의도 |
| 응용 실행 흐름 | 하나의 요청을 어떤 순서로 수행하고 확정하는가 | 필요한 모델 조회 → 도메인 행위 실행 → 결과 저장·후속 처리 |

이 관점에서 도메인 모델을 설명할 때는 응용 서비스의 호출 순서를 제외하는 것이 맞겠다는 생각으로 이어졌다. 다만 도메인 모델은 데이터 사이의 연관만 뜻하지 않는다. 상태, 행위, 계산과 허용 규칙, 불변식, 필요한 도메인 서비스까지 포함한다. 응용 서비스 안에 업무 규칙이 섞여 있다면, 그 규칙까지 무시해서는 안 되고 모델의 책임으로 검토해야 한다.

그러면 응용 서비스가 담당하는 트랜잭션은 어디에 명세해야 하는가라는 질문이 남았다. 도메인 문서에서 응용 흐름을 제외하면, 여러 도메인의 변경을 함께 성공시키거나 실패 시 취소해야 한다는 계약을 기록할 자리가 별도로 필요하다. 무엇을 함께 확정해야 하는지는 기능의 성공·실패 계약이고, 이를 어떤 DB 명령으로 구현하는지는 구현 설계다.

여기서 현재의 기능 명세가 무엇을 위한 문서인지 다시 생각하게 되었다. 도메인 아래에 붙이는 명세라면 그 도메인의 로직과 규칙을 명확히 하고 검증하는 데 쓰는 것이 자연스럽다. 정확히는 명세가 계약을 정의하고 테스트가 이를 검증한다. 반면 “이런 사용자 기능을 만들겠다”는 요구는 여러 도메인을 엮는 경우가 많아서, 하나의 도메인 아래에 기능 전체를 넣으면 책임이 왜곡되거나 중복될 수 있다.

대화에서 정리한 방향은 다음과 같다.

| 문서 | 맡을 내용 | N턴 후 아이템 획득과 연결한 예 |
|---|---|---|
| 도메인 설명 | 업무 목적, 핵심 개념, 소유권, 모델의 관계와 책임 | 대화 진행이 관리하는 상태와 트리거·아이템 영역의 관계 |
| 도메인 규칙 명세 | 각 도메인이 보장할 조건, 상태 전이, 계산 규칙, 불변식 | 어떤 턴에 보상 자격이 생기는가, 같은 발생의 중복 실행을 어떻게 금지하는가 |
| 응용 유스케이스 명세 | 사용자 목표, 참여 도메인, 성공·실패 결과, 트랜잭션 범위, 재시도 계약 | 대화 한 턴의 진행·이력·티켓·지급 요청을 어떤 성공 기준으로 연결하는가 |
| 구현 설계 | 위 계약을 실현하는 서비스 호출과 저장·통신 방식 | DB 트랜잭션, 조건부 저장, Outbox와 후속 처리 |

응용 유스케이스 하나가 여러 도메인의 규칙 명세를 참조하게 하면, 사용자 기능을 전체 흐름으로 이해하면서도 각 도메인의 책임을 유지할 수 있다. 검증도 각 도메인의 규칙 검증과 여러 도메인이 협력하는 성공·실패 검증을 구분해서 연결할 수 있다.

현재 Orbit은 도메인마다 기능 명세 하나를 연결하는 구조라서 이 구분을 충분히 표현하기 어렵다는 점도 확인했다. 기존 기능 표에는 도메인 규칙, 응용 흐름, 저장·전송 관련 검증이 섞여 있다. 기능 이름을 읽기 쉽게 바꾸거나 테스트 연결을 완성하는 것만으로는 문서의 수준과 책임이 자동으로 정리되지 않는다. 도메인 규칙 명세와 여러 도메인을 연결하는 유스케이스 명세를 별도로 다룰 구조가 필요하다는 방향까지 논의했다.

아직 구체적으로 결정해야 할 것은 남아 있다.

- 어떤 기준으로 업무를 하위 도메인으로 나누고, 어디부터 개별 기능이나 내부 모델로 설명할 것인가.
- 업무 분류 트리와 실제 도메인 모델 관계도를 Orbit에서 어떻게 함께 보여줄 것인가.
- 유스케이스 명세를 어디에 두고, 여러 도메인의 규칙 명세와 어떻게 연결할 것인가.
- 기존 명세의 항목과 테스트를 도메인 규칙·응용 계약·기술 검증으로 어떻게 재분류할 것인가.
- 문서와 코드의 개념·행위·관계가 맞는지 어떤 기준으로 계속 확인할 것인가.
