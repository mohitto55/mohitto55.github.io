# Chapter 03: 애그리거트

## 한 줄 요약

애그리거트는 **변경의 일관성을 함께 지켜야 하는 도메인 객체를 하나로 묶은 단위**이며, 외부에서는 루트를 통해서만 내부를 변경한다.

## 애그리거트가 필요한 이유

도메인이 커지면 엔티티와 밸류 객체가 많아지고, 객체 하나씩만 보면 전체 관계와 변경 범위를 파악하기 어렵다. 예를 들어 주문에는 주문자, 주문 항목, 배송 정보, 결제 정보가 연결된다. 이 객체들이 어떤 규칙을 함께 지켜야 하는지 알지 못하면, 기능 하나를 수정하다가 전체 모델의 일관성을 깨뜨릴 수 있다.

**애그리거트** 는 관련 객체를 묶어 상위 수준에서 모델을 바라보게 해 준다. 모든 연관 객체를 한 덩어리로 묶는 것이 아니라, 같은 규칙과 생명주기를 공유하는 객체를 관리 가능한 단위로 묶는다.

```
주문 애그리거트
└─ Order (애그리거트 루트)
   ├─ OrderLine[]  : 주문 항목
   ├─ ShippingInfo : 배송 정보
   └─ Orderer      : 주문자 정보

상품 애그리거트             회원 애그리거트
└─ Product                  └─ Member
```

한 애그리거트가 다른 애그리거트의 상태까지 직접 관리하지 않는다.

## 애그리거트 경계 정하기

'A가 B를 가진다'는 관계만으로 A와 B를 한 애그리거트로 묶으면 안 된다. 다음을 기준으로 판단한다.

- 두 객체는 반드시 함께 생성,삭제되는가?
- 하나를 변경할 때 다른 객체의 규칙도 같은 트랜잭션 안에서 지켜야 하는가?
- 둘의 변경 빈도와 생명주기가 비슷한가?
- 독립적으로 조회·변경될 필요가 있는가?

주문이 상품을 참조하더라도 상품의 가격 변경과 주문의 배송지 변경은 독립적이다. 따라서 Order와 Product를 하나의 애그리거트로 만들지 않는다. 주문 시점의 상품명·가격은 OrderLine에 값으로 보관해 과거 주문의 상태를 유지할 수 있다.

> 애그리거트는 크게 만들수록 편해 보이지만, 한 번에 읽고 잠그고 저장할 데이터가 늘어난다. 처음에는 작게 나누고, 반드시 함께 일관성을 유지해야 할 규칙이 있을 때만 묶는 편이 안전하다.

## 애그리거트 루트와 일관성

각 애그리거트에는 외부에 공개되는 대표 엔티티인 **애그리거트 루트(Aggregate Root)** 가 있다. 외부 객체는 내부 엔티티나 밸류를 직접 바꾸지 않고 루트의 기능을 호출한다.

루트는 애그리거트 전체의 규칙을 검사하고, 내부 구성요소를 조정해 규칙을 만족하는 상태만 만들도록 한다.

OrderLine 목록을 외부에 그대로 공개해 `add()`나 `remove()`를 허용하면 “주문 항목은 최소 한 개” 같은 규칙이 쉽게 깨진다. 루트가 의미 있는 행동을 제공해야 규칙과 변경이 한 곳에 모인다.

| 규칙 | 루트가 보장하는 방법 |
| --- | --- |
| 주문 항목은 하나 이상 | 생성·변경 시 빈 목록을 거부한다. |
| 총 주문 금액은 항목 합계와 동일 | 항목 변경 뒤 총액을 다시 계산한다. |
| 배송 시작 후 배송지 변경 불가 | 상태를 확인한 뒤에만 변경을 허용한다. |

## 리포지터리와 트랜잭션

리포지터리는 애그리거트 단위로 존재한다.

응용 서비스는 한 주문 애그리거트를 가져와 루트의 메서드를 호출하고 저장한다. 이 작업 전체를 하나의 트랜잭션으로 묶으면 애그리거트 내부 규칙이 깨지지 않은 상태로 저장된다.

```text
트랜잭션 시작 → Order 조회 → order.changeShippingInfo(...) → Order 저장 → 커밋
```

한 트랜잭션에서는 보통 한 애그리거트만 수정한다. 여러 애그리거트를 동시에 바꾸면 잠금 범위가 커지고 동시성 문제가 복잡해진다. 정말 필요한 경우에는 도메인 서비스, 이벤트, 후속 처리 등으로 조율하는 방법을 검토한다.

## 다른 애그리거트 참조하기: 객체 대신 ID

애그리거트가 다른 애그리거트를 직접 객체로 참조하면 불필요한 로딩과 수정 전파가 생기기 쉽다. Order가 Member 객체를 직접 참조하기보다 MemberId를 보관하면 주문은 회원 애그리거트에 덜 의존한다.

필요할 때 응용 서비스가 MemberId 로 회원을 조회한다. 이 방식은 경계를 분명히 하고 다른 애그리거트를 수정하려는 실수를 줄인다. 다만 목록 화면처럼 관련 데이터를 자주 함께 조회하면 성능 문제가 생길 수 있으므로, 조회 전용 모델이나 별도 쿼리를 함께 고려한다.

## 애그리거트를 팩토리로 사용하기

어떤 애그리거트의 생성 가능 여부를 판단하려면 다른 애그리거트의 상태가 필요할 수 있다.
생성 과정이 복잡해져 결합이 커진다면 별도 팩토리나 응용 서비스를 선택하는 편이 낫다.
