엔티티는 꼭 불변객체일 필요가 없고 change 함수등을 통해서 수정 가능하다.<br>OrderRepository.save()는 반환값도 없어<br>
여러 응용 서비스가 같은 Repository를 사용하는 건 맞아

  저자 예제의 ChangeShippingService와 CancelOrderService는 둘 다 OrderRepository로
  주문을 조회하고 변경해. 저장을 요청하는 응용 서비스가 시스템 전체에서 하나여야 한다는
  구조가 아니야.<br>
 2. 엔티티 불변성과 밸류 객체 불변성은 구분해야 해

  공식 예제에서:

  - 엔티티 Order.cancel()은 기존 객체의 상태를 변경하고 반환값은 없어.
  - 밸류 객체 Money.multiply()는 새로운 Money를 반환해.

  즉, 엔티티까지 전부 불변으로 만들어야 한다는 방식은 아니야. 핵심은 무분별한 setter
  대신 업무 행위가 규칙을 검증하는 거야.<br>
### 4. Repository 싱글톤과 엔티티 공유는 다른 문제야

  상태 없는 Repository 구현을 싱글톤으로 주입할 수는 있어. 그렇다고 여러 요청이 동일한
  엔티티 인스턴스나 UoW까지 전역으로 공유하는 건 아니야. 싱글톤·팩토리는 객체 생성·수명
  관리 방식이지, 저장 일관성을 보장하는 장치는 아니야.
